# Project Context for Claude Code

This file is read automatically by Claude Code when it starts in this folder. It exists so a fresh session has the full picture without the user re-explaining everything.

## What this is

A dissertation project: "A Centralized Disaster Aid Request, Tracking and Distribution Management System for Sri Lanka" — BSc Software Engineering, NSBM Green University. Connects disaster victims, donors, volunteers, and admins on one platform: victims submit aid requests (multiple resource categories per request, each capped), a rule-based algorithm prioritizes them, donors register donations (choosing self-delivery or volunteer-assisted), admins match donations to requests and assign volunteers (volunteers can accept/reject), volunteers deliver, victims confirm receipt **by scanning a QR code the deliverer shows them** (not a same-device button tap). A public map (embedded on the landing page and at `/severity-map`) shows aggregated affected-area severity by district plus live river-gauge levels; a separate admin-only map at `/admin/map` adds exact pinpoint request/donation locations. The UI is available in English, Sinhala, and Tamil. Photo evidence was considered and explicitly declined (see "Known scope cuts" below — needs Firebase Storage on the paid Blaze plan, and the user isn't spending more on this project). Google Maps turn-by-turn navigation for volunteers ("like PickMe") is now built and live on web; `react-native-maps` on mobile is also built and live.

The user is a beginner developer working under a tight deadline. Prioritize working code over teaching concepts unless they ask to learn something. Keep explanations short and practical. Give complete, runnable files rather than partial diffs/snippets — the user copy-pastes whole files rather than reviewing line-by-line changes.

## Tech stack (decided, do not suggest alternatives without a strong reason)

- **Backend:** Node.js + Express
- **Database + Auth:** Firebase Firestore + Firebase Authentication (Email/Password provider)
- **Web frontend:** React + Vite + TypeScript + Tailwind CSS, plain `fetch`-based API calls (no React Query/SWR)
- **Mobile:** Expo / React Native, TypeScript. Started — see "Mobile app (Expo / React Native)" below for what's built, what's stubbed, and the setup gotchas.
- **Maps — two different tools for two different jobs, don't conflate them:**
  - **Leaflet + react-leaflet + OpenStreetMap** (free, no API key) — built and live for the admin situation map (`/admin/map`) and the public severity map (`/severity-map`). `react-leaflet@^4` specifically (v5 requires React 19; this project is on React 18.3).
  - **Google Maps Platform (Maps JavaScript API + Maps SDK for Android + Routes API)** — approved by the user, willing to pay, **billing enabled and budget alert set**. Deliberately **Routes API, not the legacy Directions API** — the user's explicit direction for anything started in 2026 — called directly via its REST endpoint (`computeRoutes`), not through `@react-google-maps/api`'s `DirectionsService`/`DirectionsRenderer`, which only speak the legacy API. Requests the cheapest field mask (route line + distance/duration, no per-step text) per the user's own cost-consciousness — see "Turn-by-turn volunteer navigation" below for the full story, including why this doesn't avoid needing billing enabled. Volunteer turn-by-turn navigation ("like PickMe") is **built and live on web**. `react-native-maps` on mobile is **also built** (see "Mobile maps" below) — severity map (victim/donor/volunteer) + admin situation map, both compiling clean, not yet verified on-device pending a fresh `eas build` with the native module linked in. Do not use Google Maps for anything Leaflet already handles for free.
- **Weather:** OpenWeatherMap — built and live (see "Weather (OpenWeatherMap)" below). `OPENWEATHER_API_KEY` is set in `server/.env` and confirmed returning real data.
- **External disaster data — built, using what was actually found by researching the real DMC site (not guessed):**
  - **DMC Emergency Warnings RSS** (`https://www.dmc.gov.lk/index.php?option=com_content&view=category&layout=blog&id=16&Itemid=237&format=feed&type=rss&lang=en`) — real, working, standard RSS 2.0. Parsed with `fast-xml-parser`. Frequently empty (no active warning) — that's DMC's actual state, not a bug.
  - **DMC Situation Reports / Water Level bulletins** — turned out to be **PDF-only**, no structured data on the page itself (title/date/time/download-link rows, actual numbers locked inside each PDF). Deliberately NOT scraped/parsed — PDF text extraction is high-effort and fragile for the value it adds here. Not built.
  - **Live river gauge levels** — now the Department of Irrigation's own official ArcGIS Online feature service (`gauges_2_view`), not a third-party proxy. See "River gauges — switched to the official Irrigation Department source" below for the full story of how this was found and verified.
  - **Reservoir storage / spilling risk monitoring** — two separate sources for two separate operators: the Irrigation Department's own daily Major/Medium Reservoir Water Level bulletin (109 irrigation reservoirs, a published Google Sheet), plus CEB/Mahaweli Complex's public daily bulletin (Kotmale/Victoria/Randenigala hydropower reservoirs, scraped from `mahawelicomplex.lk`'s public login-page HTML). Both risk-categorized (normal/elevated/near-capacity/spilling) and wired into the same area-alert pipeline. See "Reservoir risk monitoring" below.
  - **GDACS (Global Disaster Alert and Coordination System, EC Joint Research Centre)** — tropical cyclone tracking + general disaster events (earthquakes, floods, droughts, wildfires) worldwide, filtered to ones relevant to Sri Lanka. The GeoJSON REST API originally requested (`gdacsapi/api/Events/geteventlist/SEARCH`) was tested repeatedly (~10 attempts, varied query params, several minutes apart) and consistently failed — either a connection timeout or GDACS's own backend returning `"Timeout expired... obtaining a connection from the pool... max pool size was reached"`, a server-side error on their end. Their RSS feed (`https://www.gdacs.org/xml/rss.xml`) was reliably reachable and has richer per-event data than the REST API's shape was ever confirmed to have — used instead. Same pattern as the DMC PDF-vs-RSS decision below: verify what actually works, use that, document the substitution rather than silently forcing the originally-requested source.
  - This whole area was excluded in the dissertation's own Chapter 1 and the user chose to build it anyway with that tradeoff explicitly acknowledged (see "Known scope deviation" below).
- **Notifications:** Firebase Cloud Messaging — built (see "Push notifications (FCM)" below). `VITE_FIREBASE_VAPID_KEY` is now set in `web/.env` and confirmed working — see "Push notifications (FCM)" below for how this was verified without a real device. **Real SMS via Text.lk is now also built alongside FCM** (see "Real SMS (Text.lk)" below) — reopened after initially being cut for Twilio needing a paid/verified business account (and, separately, Twilio doesn't operate in Sri Lanka at all); the user redirected to Text.lk, a Sri Lankan SMS gateway, and provided a real API token. Both channels fire in parallel at the same trigger points — SMS doesn't replace FCM, it sits alongside it. `TEXTLK_API_TOKEN` is live in `server/.env` and has been test-fired once already (see "Real SMS (Text.lk)" below) — real SMS delivery is confirmed working.
- **Hosting (not done yet):** web → Firebase Hosting; API → Render or Railway free tier

Note: the UI was originally scaffolded in Lovable.ai (defaults to Supabase) — rejected in favor of Firebase, web app rebuilt from scratch. If Supabase references appear anywhere, they're cruft to remove, not a signal to reintroduce it.

## Data model (Firestore collections)

### users
`{uid, email, name, role: "victim"|"donor"|"volunteer"|"admin", phone, location, nic, homeAddress, available, createdAt}`. `nic`/`homeAddress` only populated for role "victim" (both `null` otherwise, and `null` for victim accounts created before this field existed) — `nic` is unique across victim accounts, both feed the `possibleDuplicate` check on new requests. Sensitive PII — see Privacy section, non-negotiable constraints on where these can ever appear. `available` (boolean) only meaningful for role "volunteer" — absent on existing volunteer docs pre-dating this field, always treated as `available !== false` (i.e. missing = available) rather than requiring a backfill, see "Volunteer availability toggle" below.

### aidRequests
`{victimId, victimName, victimNic, victimHomeAddress (both normalized, or null for pre-existing accounts), possibleDuplicate, disasterType, items: [{category, quantity, unit, status: "pending"|"matched"|"delivered", donationId}], requestedCategories: string[] (denormalized item categories, for array-contains matching queries), severity, peopleAffected, vulnerableGroups[], location, notes, status: "pending"|"verified"|"rejected"|"in_progress"|"delivered", priorityScore, priorityBreakdown, createdAt, updatedAt, verifiedAt}`. A request can ask for several categories at once, each capped (see `server/src/utils/categories.js` — medicine has no cap but is instead flagged for review). Overall `status` is derived from item statuses via `computeOverallStatus()` — `in_progress` means at least one item matched/delivered but not all delivered yet. `possibleDuplicate` is a flag for admin attention, not a block — set when an existing active request shares the same NIC or home address. `verifiedAt` is set once, the first time a request is approved (never overwritten on a later re-verify) — absent on rejected or still-pending requests; powers the admin dashboard's average time-to-verification KPI, see "Admin dashboard KPIs" below.

### donations
`{donorId, donorName, category, quantity, location, deliveryMethod: "self"|"volunteer", notes, status: "available"|"matched"|"delivered", matchedRequestId, assignedDeliveryId, deliveryStatus (mirrors the active delivery's status, or null), lastRejectionReason (set when a volunteer rejects, cleared when the next one accepts), createdAt, updatedAt}`. One donation still targets exactly one category — a multi-category request gets fulfilled by several separate donations/deliveries, one per category.

### deliveries
`{requestId, donationId, category, volunteerId (null for self-delivery), method: "self"|"volunteer", status: "pending_acceptance"|"accepted"|"rejected"|"picked_up"|"delivered"|"confirmed", rejectionReason, confirmToken (set once status reaches "delivered"), currentLocation: {lat,lng}|null, createdAt, updatedAt}`. Volunteer deliveries start at `pending_acceptance` and need an explicit accept before progressing; a reject resets `donations.assignedDeliveryId`/`deliveryStatus` to null so admin can assign someone else (the request item stays `matched` throughout). Self-delivery donations skip straight to `accepted` (auto-created at match time) and the donor marks `delivered` directly (no `picked_up` step).

### categoryLimits
`{label, max: number|null, unit, createdAt, updatedAt}`, one doc per category, doc ID = a slugified key derived from the label (lowercase, non-alphanumeric → `_`, trimmed). `max: null` means no fixed cap (medicine — always flagged for admin review instead, see `requests.js`). Self-seeds from `DEFAULT_CATEGORY_LIMITS` in `server/src/utils/categories.js` the first time the collection is read empty; after that Firestore is the sole source of truth — the defaults constant is a seed value only, not consulted again.

### broadcasts
`{message, severity: "info"|"warning"|"critical", active: boolean, createdBy, createdByName, createdAt, updatedAt, deactivatedAt}`. Only one broadcast is ever `active: true` at a time — posting a new one deactivates the current one in the same batch write, so there's a full history rather than a single mutable doc. Nothing self-seeds here; an empty collection just means no banner has ever been posted.

### caseNotes
`{requestId, authorId, authorName, text, createdAt}`. Top-level collection (not a subcollection of `aidRequests`, consistent with how `deliveries`/`donations` reference their parent by id rather than nesting) — one doc per note, append-only, no edit or delete. Fetched with a single `where("requestId", "==", ...)` and sorted by `createdAt` in JS rather than `orderBy` in the query, deliberately, to avoid needing a Firestore composite index (see "Internal case notes" below for why this matters).

### auditLog
`{action, actorId, actorName, targetType, targetId, details, createdAt}`. Append-only, admin-read-only. `action` is one of `request.approve` / `request.reject` / `request.bulk_approve` / `request.bulk_reject` / `donation.match` / `delivery.assign` / `delivery.reassign` / `district.activate` / `district.deactivate` / `area_alert.approve` / `area_alert.reject` / `sos.status_update` / `community_report.verify` / `community_report.dismiss` / `flood_model.retrain` (this list has grown past what earlier handoffs kept updated here — `AuditLog.tsx`'s `ACTION_LABELS` map is the actual source of truth if this drifts again); `details` is a small action-specific object (e.g. `{victimName}` for a verify, `{ids, count}` for a bulk verify, `{category, matchedRequestId, deliveryId}` for a match, `{requestId, donationId, volunteerId}` for an assign, `{district, sourceAlertTitle}` for a district activate/deactivate). See "Audit log" and "Active emergency districts" below.

### activeDistricts
`{district, activatedAt, activatedBy, activatedByName, sourceAlertTitle}`, doc ID = slugified district name (e.g. `colombo`), one doc per **currently active** district — deactivating deletes the doc rather than flipping a boolean, so "does this doc exist" is the whole active/inactive check. `sourceAlertTitle` is set when activation came from the DMC-alert quick-action on `/admin/map`, `null` for a manual activation from `/admin/active-emergencies`. Public read (no PII), admin-only write. See "Active emergency districts" below.

### deliveryChats
`{deliveryId, requestId, donationId, pairKey: "donor_volunteer"|"volunteer_victim"|"donor_victim", partyAId, partyARole, partyBId, partyBRole, consentA, consentB, contactRevealed, status: "active"|"locked", createdAt, updatedAt}`. Doc ID is the deterministic `${deliveryId}_${pairKey}`. One chat per (delivery, pair) — a volunteer-delivery gets two (donor↔volunteer, volunteer↔victim), a self-delivery gets one (donor↔victim). Real name/phone are never stored here — only resolved on demand once `contactRevealed` is true. See "Delivery chat + consent-gated contact sharing" below.

### chatMessages
`{chatId, senderId, senderRole, text, createdAt}`. Top-level collection (same "reference the parent by id, don't nest" convention as `caseNotes`), append-only, sorted by `createdAt` in JS to avoid a composite index. See "Delivery chat + consent-gated contact sharing" below.

## Category management

Category caps used to be a hardcoded object requiring a code deploy to change. Now admin-editable at runtime:
- `server/src/utils/categories.js` — `getCategoryLimits()`, the shared async accessor every route uses (self-seeding, see above).
- `server/src/routes/categories.js` — `GET /api/categories` (any authed user — victim/donor forms need it too), `POST /api/categories` (admin, add a new category), `PATCH /api/categories/:key` (admin, adjust an existing category's cap/label/unit).
- `AdminCategories.tsx` (`/admin/categories`) — admin UI: inline cap editing per category + a form to add new ones.
- `VictimRequestForm.tsx` and `DonorDonationForm.tsx` both fetch `GET /api/categories` on mount instead of using a hardcoded list — a category added via the admin UI is immediately requestable and donatable with no code change. `VictimRequestForm.tsx` falls back to the raw Firestore `label` (via i18next's default-value param, `t(\`categories.${key}\`, limit.label)`) for any category not present in the locale JSON files — so new categories show in English until someone adds translated strings, rather than showing a raw i18n key.
- `requests.js` and `donations.js` both validate against `getCategoryLimits()` at request time rather than an imported constant — a cap change or new category takes effect on the very next request, no restart needed.
- Verified live end-to-end: lowered the baby-formula cap (4→2 tins) and confirmed the server rejects a 3-tin request with the updated number in the error message; added a new "Tarpaulins" category and confirmed it appeared in and was usable from both the victim request form and the donor donation form without any code change.

## Emergency broadcast banner

The manual, admin-curated equivalent of the DMC alerts feed — for messages the DMC RSS won't have (e.g. "Cyclone approaching Batticaloa, expect delivery delays").

- `server/src/routes/broadcasts.js` — `GET /active` (public, returns the current banner or `null`), `GET /` (admin, last 20 for history), `POST /` (admin, posts a new banner; body `{message, severity}`, severity defaults to `"warning"`), `PATCH /:id/deactivate` (admin, clears without replacing). Posting a new banner and deactivating the previous one happens in a single Firestore batch, so there's never a moment with two banners active.
- `AdminBroadcast.tsx` (`/admin/broadcast`) — shows the current active banner with a "Clear banner" button, a form to post a new one (message + severity: info/warning/critical), and a short history list below.
- `EmergencyBanner.tsx` — fetches `GET /api/broadcasts/active` once on mount and renders a colored bar (blue/amber/red by severity) with a "Close" button. Closing is **session-only** (the dismissed broadcast's id is stashed in `sessionStorage`) — it hides the banner for that browser tab's session, it does **not** deactivate it for anyone else. Only an admin clearing it from `/admin/broadcast` actually removes it for everyone.
- Embedded in two places: `Landing.tsx` (top of the public page, above the header) and `DashboardLayout.tsx` (top of the page, above the sidebar+content row, so every logged-in role — victim, donor, volunteer, admin — sees it regardless of which dashboard page they're on).
- No live-update mechanism yet — the banner is fetched once per page load, so if an admin posts a banner while a user already has a page open, they won't see it until they navigate or refresh. ## Internal case notes

A small, per-request comment thread for admin-to-admin handoff context ("called the victim, they confirmed access road is passable") — separate from the emergency broadcast banner, which is public-facing and one-at-a-time.

## Live updates (Firestore `onSnapshot`)

Directly answers dissertation Research Question 2 ("how can real-time digital information sharing improve collaboration") — demonstrable live in the viva: open `/admin/requests` in one browser, submit a request as a victim in another, watch it appear with no refresh.

- **Architecture: reads go live, writes stay on the Express API.** `AdminRequests.tsx`, `AdminDonations.tsx`, and `EmergencyBanner.tsx` now subscribe directly to Firestore via the client SDK's `onSnapshot` instead of a one-time `apiFetch` — `web/src/lib/firebase.ts` exports `db` (`getFirestore(firebaseApp)`) for this. Every *write* (verify, match, assign, post a banner, etc.) still goes through the Express backend exactly as before, because that's where business-rule validation lives (priority scoring, category caps, one-active-banner-at-a-time). The listener just means the UI updates the instant Firestore's data changes, regardless of whether that change came from this browser tab, another admin's tab, or the backend — no manual `load()`/refetch needed after a mutation.
- `AdminRequests.tsx` subscribes to the whole `aidRequests` collection unfiltered and sorts by `priorityScore` in JS (same sort as before, just now live). `AdminDonations.tsx` subscribes to `donations` the same way; its volunteer list stays a one-time `apiFetch` since that data doesn't need to be live. `EmergencyBanner.tsx` uses a `where("active", "==", true), limit(1)` query instead of `GET /api/broadcasts/active` — this is the one live listener that also runs for **logged-out** users on the public landing page.
- **Important discovery made while building this, corrects a wrong assumption repeated across earlier handoffs of this file:** Firestore security rules were believed to be undeployed/"test mode." They were not — `firestore-rules/firestore.rules` (deployed via `firebase deploy --only firestore:rules`, config in `firebase.json`/`.firebaserc`) was already live and enforced, which is exactly why building this feature surfaced a real bug: `broadcasts`, `categoryLimits`, and `caseNotes` had **zero rule coverage**, so `EmergencyBanner.tsx`'s direct read was silently denied (`permission-denied`) even though the same data was readable fine through the Express backend (Admin SDK bypasses rules entirely — this is why the gap went unnoticed until a client made a *direct* Firestore read). Fixed by adding rule blocks for all three collections and redeploying — confirmed with the user before deploying, since it's a live security change. See the corrected note in "Privacy and security notes" below.
- Verified live end-to-end, three separate ways: (1) approved a request via a `curl` call to the Express API while `/admin/requests` stayed open in a browser with no reload — the row's status and action buttons updated instantly; (2) mutated a donation's `status` field directly via the Admin SDK (bypassing the Express API entirely, simulating any external writer) while `/admin/donations` stayed open — same instant update, confirming this isn't just an artifact of the app's own fetch calls; (3) posted and then deactivated a broadcast via the API while the **logged-out** public landing page stayed open — the banner appeared and disappeared live, proving the public read path works under the newly-deployed rules, not just the authenticated admin path.

## Stale request flags

Auto-highlights anything sitting unactioned too long, so an urgent case doesn't silently sink to the bottom of a long, priority-sorted list.

- Purely a derived/computed flag on `AdminRequests.tsx` — no new backend endpoint, no new Firestore field. `isStale(r)` is true when `status` is `"pending"` or `"verified"` (i.e. no item has matched yet — `"in_progress"` already means something moved) **and** `createdAt` is older than an admin-adjustable threshold (number input in the filter bar, default 6 hours).
- Stale rows get an amber `⏱ Stale (Nh)` badge in the existing Flags column (age shown in hours, or days once past 48h) and a subtle amber row tint — distinct from the blue selection tint, which still takes priority when a row is both selected and stale.
- A "Stale only" checkbox in the filter bar composes with every other filter (name/type/status/district/date range) the same way, since it's just one more clause in the same `filteredRequests` `useMemo`.
- **One real wrinkle worth remembering:** staleness changes purely because *time passes*, not because Firestore data changed — the existing `onSnapshot` listener only re-renders on a write. Without something extra, a request sitting at 5h59m wouldn't visibly flip to "stale" until some unrelated write happened to touch the collection. Fixed with a `setInterval` that ticks a dummy state value every 60 seconds purely to force a re-render (included as a dependency of the `filteredRequests` memo) — cheap, and the right fix for any future feature whose truth value depends on wall-clock time rather than data.
- Verified live: backdated one seed request's `createdAt` to 9 hours ago directly via the Admin SDK and confirmed it picked up "⏱ Stale (9h)" and the amber tint with no reload; independently, a different seed request already showed "⏱ Stale (24h)" on its own from real elapsed time, confirming the age math wasn't just matching the one forced test case. Toggling "Stale only" correctly narrowed the table to exactly those two rows ("Showing 2 of 7"); raising the threshold to 30h correctly excluded both ("Showing 0 of 7"). Reverted the backdated timestamp afterward.

## Automatic volunteer assignment

Restores the original workflow described in the dissertation's Chapter 02 (§2.5.3, step 6) — "Available volunteers are assigned to matched request-donation pairs based on proximity to the donation pickup location" — which the earlier manual-dropdown-only version had deviated from. Decided while writing the thesis's Chapter 4 (SRS); two open questions were confirmed with the user before building: **the rule** is nearest-available-volunteer by Haversine distance, tie-broken by fewest active deliveries; **manual assignment stays** as an admin override, not replaced outright.

- **`server/src/utils/autoAssignVolunteer.js`** — `findBestVolunteer(pickupLocation)`. Queries `users` where `role == "volunteer"`, filters to `available !== false` **and has a `location` on file** in JS (not a second Firestore `where`, avoiding a composite-index dependency — same convention as "Internal case notes"), ranks by `distanceKm()` (reusing `server/src/utils/geo.js`, the same function `donations.js` already uses for donation-to-request matching), tie-broken by each candidate's count of deliveries in `ACTIVE_DELIVERY_STATUSES` (`pending_acceptance`/`accepted`/`picked_up` — same "active" definition `VolunteerWorkload.tsx` already uses). Returns `null` if nobody qualifies, rather than throwing — matching is never blocked by assignment failing.
- **A real gap this surfaced, not initially obvious: volunteers never had a location to rank by.** `Register.tsx` never captures one for any role, so `users.location` was always `null` for volunteers — "nearest by distance" would have silently never matched anyone. Fixed with a new **`PATCH /api/users/location`** endpoint (volunteer-only, same self-owned-field pattern as `PATCH /availability`) and a **"Set my location" pill on `VolunteerDeliveries.tsx`**, right next to the existing availability toggle — amber when unset, green "Location set — update" once captured, with the same `navigator.geolocation` pattern used elsewhere in this app. A volunteer who's available but hasn't set a location simply isn't eligible for auto-assignment yet (still shows up in the manual "Reassign" dropdown, which isn't distance-aware) — no backfill, no forced prompt, just opt-in like every other self-owned field in this project.
- **`donations.js`'s `POST /:id/match`** now calls `findBestVolunteer()` for volunteer-delivery donations (self-delivery is untouched — it already auto-creates its own accepted delivery, no volunteer involved) right after the request match, auto-creating the `pending_acceptance` delivery in the same request/response cycle rather than requiring a second admin action. Logs `delivery.assign` with `details.source: "auto"`. If nobody qualifies, the donation is left unassigned exactly like before this feature existed, and the response's `autoAssignedVolunteer` field is `null` so the frontend can say so.
- **`deliveries.js`'s `POST /` is now also the reassign path**, not just fresh-assign. If the donation already has a delivery: reassigning is allowed (updates the *same* delivery doc's `volunteerId`, keeps `status: "pending_acceptance"`, logs `delivery.reassign` with `previousVolunteerId`) only while that delivery is still `pending_acceptance`; once the volunteer has accepted (or moved further), it's blocked with a 409 — swapping volunteers on someone already committed would corrupt state they're actively acting on. Deliberately updates the existing doc rather than creating a new one, so nothing downstream (the volunteer's `GET /mine` list, QR confirmation, audit log) needs a second doc to reconcile.
- **`AdminDonations.tsx`** — "Find match" now surfaces who got auto-assigned ("Auto-assigned to X (nearest available)") or that nobody qualified. The volunteer picker no longer only appears when unassigned — it also appears (relabeled "Reassign to...") whenever a delivery is still `pending_acceptance`, and disappears once accepted, matching exactly what the backend allows.
- **`AuditLog.tsx`** — `delivery.assign` entries now show the volunteer's name and, when auto-assigned, "(auto-assigned, nearest available)"; a new `delivery.reassign` entry type shows both the new and previous volunteer.
- Verified end-to-end via real HTTP calls (temp admin + 2 temp volunteers at different simulated locations + a donor + a victim, real Firebase ID tokens): matched a volunteer-delivery donation and confirmed the **nearer** of the two volunteers was auto-assigned, not the farther one; reassigned to the second volunteer while still `pending_acceptance` and confirmed it succeeded and updated the same delivery doc; had that volunteer accept, then confirmed a further reassign attempt was correctly rejected with 409; confirmed both a `delivery.assign` (`source: "auto"`) and a `delivery.reassign` (`previousVolunteerId` set) audit entry were recorded with accurate details. Also click-verified in the browser: registered a throwaway volunteer, confirmed the "Set my location"/"Available for new deliveries" pills render correctly side by side, and confirmed clicking "Set my location" correctly shows the "Couldn't get your location" error state — this browser automation environment can't grant geolocation permission (same known limitation already noted elsewhere in this file for QR camera scanning and the active-districts soft note). ## Admin dashboard KPIs

The last item on the user's operational-features list — turns `/dashboard` from a quick-links menu into an actual command-center view for the admin role specifically (other roles are unchanged).

- `Dashboard.tsx` — a new `AdminKpiRow` component, rendered only when `profile.role === "admin"`, sits above the existing quick-links grid on the same shared `/dashboard` route. Subscribes live via `onSnapshot` to `aidRequests`, `donations`, and `deliveries` (same pattern as every other admin view) and renders four `StatCard`s (the same shared component used on `Landing.tsx`/`TransparencyDashboard.tsx`):
  - **Pending requests** — count of `aidRequests` with `status === "pending"`.
  - **Unmatched donations** — count of `donations` with `status === "available"`.
  - **Active deliveries** — count of `deliveries` with `status` in `pending_acceptance`/`accepted`/`picked_up` (same `ACTIVE_STATUSES` concept as "Volunteer workload view").
  - **Avg. time to verification** — average of `verifiedAt - createdAt` across every request that has ever been verified (regardless of what status it's since moved to), formatted as minutes/hours/days depending on magnitude. Shows "—" when no request has been verified yet, rather than 0 or NaN.
- **Needed a real backend change to be accurate, not just a frontend view:** averaging verification time requires knowing exactly when each request was first approved. `updatedAt` doesn't work for this — it gets overwritten by every subsequent change (matched, delivered, etc.), so it stops meaning "time of verification" the moment a verified request progresses further. ### Cyclone track polygon + colored marker on `/admin/map`

A follow-on request: draw the storm's geometry on the existing Leaflet map, not just list it as text.

- **The RSS `<item>` itself has no geometry beyond a single current point — had to go find the real per-event geometry resource, not guess a field name.** GDACS's `/gdacsapi/api/polygons/getgeometry` endpoint (the natural guess for a "geometryUrl") is under the same `/gdacsapi/` path as the broken `geteventlist/SEARCH` API and failed with the identical connection-timeout pattern — confirmed by testing it directly, not assumed to be broken by association. What does work: every RSS item's `gdacs:cap` field links to that event's **CAP (Common Alerting Protocol) XML** file, served from a different path (`/contentdata/resources/...`, reliably reachable, confirmed 200). Its `<info><area><polygon>` element contains the storm's current hazard-area polygon as space-separated `lat,lng` pairs — already Leaflet's native `[lat, lng]` order, no coordinate-swap needed, confirmed by fetching a real cyclone's CAP file and parsing it (450 points, properly closed).
- **Important, honest caveat — this is the current episode's hazard/uncertainty-area polygon, not a literal multi-point historical track line.** GDACS's RSS only ever exposes the latest episode; the REST API that would provide episode-by-episode history is the same one that's down. So the polygon shown is "here's the storm's current affected-area shape," not "here's everywhere it's been." Worth knowing before describing this as track history anywhere it matters (e.g. the dissertation write-up).
- `server/src/routes/external.js` — new `fetchCapPolygon(capUrl)` helper, called for every Sri Lanka-relevant event's `capUrl` inside the same cached `GET /gdacs` response (cheap since there are rarely more than 0–2 relevant events at once). - `SituationMap.tsx` — each event renders a Leaflet `<Polygon>` (when `geometry` is present) and a `<CircleMarker>` at its current position, both colored by `alertLevel` using `GDACS_ALERT_LEAFLET_COLOR` — the exact same hex values (`#16a34a`/`#f97316`/`#dc2626`) already used by `SEVERITY_COLOR`/`AREA_LEVEL_COLOR` elsewhere on this page, just re-keyed by GDACS's Green/Orange/Red instead of a status string, so the map reads consistently regardless of which layer you're looking at. - **`GET /api/external/weather`** — public, cached 30 min (`WEATHER_CACHE_TTL_MS`). Queries OpenWeatherMap's Current Weather API (`data/2.5/weather`) — **confirmed reachable by direct query, not guessed**: hit it with no API key and got back a real, documented `401 Invalid API key` response (not a connection failure or dead host), confirming the base URL/path are correct before any code was written against it, same verify-first discipline as every other external source in this file.

## Push notifications (FCM)

Requested as "SMS alerts on every move" (request accepted, delivery started, delivery ended) plus area-wide disaster alerts to victims based on their location. Real SMS was initially ruled out as a scope cut (Twilio needs a paid/verified business account, or so it seemed at the time) and **Firebase Cloud Messaging** (free, browser/app push) was built as the sole channel instead. **SMS was later reopened and built too, alongside FCM, not instead of it** — see "Real SMS (Text.lk)" below for why and how.

- **`server/src/utils/notifications.js`** — `sendNotificationToUser(uid, {title, body, data})`, the one shared helper every trigger point below calls. Looks up `users/{uid}.fcmTokens` (an array — one user can have several devices/browsers registered), sends via `admin.messaging().sendEachForMulticast()`, and prunes any token FCM reports as dead. **Two dead-token error codes matter, not just one** — found by testing directly rather than guessing: `messaging/registration-token-not-registered` / `messaging/invalid-registration-token` (a token that was once valid and has since expired/been uninstalled) and, separately, `messaging/invalid-argument` (FCM's actual code for a malformed/non-token string — confirmed by sending a deliberately garbage token and inspecting the real response). Fails soft everywhere — a missing profile, zero tokens, or a send error never breaks the caller's actual work (verifying a request, updating a delivery).
- **`POST /api/users/fcm-token`** (any authed user) — body `{token}`, appends to `fcmTokens` via `arrayUnion` (re-registering the same token is a no-op). No new Firestore rule needed — `users/{userId}` already allows the owner to write their own doc.
- **Three trigger points, interpreting the literal ask onto this system's actual delivery lifecycle** (documented here in case a future session wonders why these three and not others): "request accepted" → `PATCH /api/requests/:id/verify` and `/bulk-verify` when `approve === true` (this is the victim's first "good news" moment, not the volunteer's own delivery-assignment accept/reject, which is a separate concept); "started delivery" → `PATCH /api/deliveries/:id/status` when the new status is `picked_up`; "end of delivery" → the same route when status is `delivered`, **and** `PATCH /api/deliveries/:id/self-deliver` (self-delivery skips `picked_up` entirely, so it only ever fires the `delivered` copy). Deliberately notifies at `delivered` ("scan to confirm") rather than `confirmed` — the victim is the one who triggers `confirmed` themselves by scanning, so telling them what they just did would be redundant; the useful moment to interrupt them is when the QR is ready to scan, not after.
- **Frontend (`web/src/lib/firebase.ts`, `lib/notifications.ts`, `components/NotificationSetup.tsx`, `public/firebase-messaging-sw.js`):** `firebase.ts` exports `messagingPromise` (an `isSupported()`-gated promise, since `getMessaging()` throws outright in browsers without Push API support — Safari <16.4, non-HTTPS/non-localhost — rather than returning `null` the way the rest of this SDK does). `NotificationSetup.tsx` is rendered once in `DashboardLayout.tsx` (so every logged-in role gets it, not just victims — no reason to restrict it given volunteers/donors could get their own notification types later) and handles the whole lifecycle: silently re-registers the token on every login if permission was already granted in a past session, shows a one-line dismissible opt-in bar if permission hasn't been decided yet (`Notification.permission === "default"`), and renders a toast for foreground messages (background messages are handled by the service worker instead — FCM never calls `onMessage` for a page that's frontmost, only `onBackgroundMessage` in the SW for everything else).
- **`public/firebase-messaging-sw.js` must live at the site root** (FCM's hard convention, not configurable) and, being a plain script the browser loads directly rather than something Vite bundles, **can't read `import.meta.env`** — its Firebase config values are hand-duplicated from `web/.env` with a comment explaining why. This is fine, not a leak: these are the same public client identifiers already documented as "not secret" in `firebase.ts`, and they already ship inside the built JS bundle sent to every visitor regardless.
- **Needs a Web Push certificate (VAPID key) the user has to generate themselves** — Firebase Console > Project Settings > Cloud Messaging tab > Web configuration > "Web Push certificates" > generate a key pair — same category of blocker as the Google Maps API key (tied to their own Firebase project, nothing to guess or placeholder around). Added `VITE_FIREBASE_VAPID_KEY=` to `web/.env` with a comment; `requestAndRegisterFcmToken()` logs a clear console warning and returns `"unsupported"` rather than throwing if it's missing. **Resolved — the user provided a real key**, now set in `web/.env`.
- **Verified as far as this dev environment allows, honestly split between what's proven and what isn't:**
  - Proven end-to-end via real HTTP calls (not just unit-testing the helper in isolation): registered a throwaway victim through the actual `/register` UI, then — since this browser automation environment reports `Notification.permission` as permanently `"denied"` (a sandbox/headless policy, not an app bug — same category of limitation already documented for camera QR scanning and geolocation) — obtained real Firebase ID tokens for temporary admin/volunteer test accounts via the Identity Toolkit REST API (`accounts:signInWithPassword`) and called the actual Express routes directly: `PATCH /:id/verify` (approve), `PATCH /:id/status` (`picked_up` then `delivered`). All three returned 200 with no server-side errors, confirming the notification call sites are wired correctly (right field names, right imports, no crashes) even though no real device ever received a push.
  - Proven directly against `sendNotificationToUser` itself: a user with zero `fcmTokens` no-ops silently; a registered token that fails to send gets pruned from Firestore automatically; both of FCM's distinct dead-token error codes are handled (found the second one, `invalid-argument`, only by testing with a real malformed token and inspecting the actual response rather than assuming one error code covered every failure mode).
  - **Confirmed the real VAPID key actually loads, without needing a grantable permission.** Once the key was added, dynamically imported `notifications.ts` in the live browser console and called `requestAndRegisterFcmToken()` directly: it returned `"denied"` (this sandbox's real, permanent `Notification.permission` value) rather than `"unsupported"` (what it returns when the key itself is missing) — and no "VAPID key not set" warning appeared in the console. This is the correct, provable distinction between "the key isn't configured" and "the key is configured but this sandbox can't grant permission" — the second is an environment limitation, not a bug.
  - **Still not proven, and genuinely can't be from this environment:** the actual browser permission-prompt UI, a real device receiving a real push notification, and the service worker's background-message handler firing — all three need a real browser with notification permission actually grantable, worth a manual phone/browser check now that the key is in place.
  - All test accounts, the test request, and the test donation/delivery created for this verification were deleted afterward via the Admin SDK, same cleanup convention used throughout this file.

## Real SMS (Text.lk)

Reopened after being cut earlier for "needs a paid/verified business account" (Twilio) — the user pointed out **Twilio doesn't actually operate in Sri Lanka** and redirected to **Text.lk**, a Sri Lankan SMS gateway, providing a real API token directly in chat. **Built alongside FCM, not as a replacement** — every trigger point below fires both channels. Built entirely from Text.lk's own published API docs (fetched and read directly, not guessed) since this provider wasn't something already known — confirmed exact endpoint, headers, and field names before writing any code against it, same verify-first discipline as every other external integration in this file.

- **API contract, confirmed from `https://text.lk/docs/send-sms/` directly:** `POST https://app.text.lk/api/v3/sms/send`, headers `Authorization: Bearer <token>` / `Content-Type: application/json` / `Accept: application/json`, body `{recipient, sender_id, type: "plain", message}`. Phone numbers use the **country code with no `+` and no leading zero** (`94771234567`, not `+94771234567` — a different format than Twilio's E.164, worth remembering if this is ever compared against the earlier Twilio version's `toE164()`).
- **`server/src/utils/phone.js`** — `normalizeSriLankanPhone(input)`, a small pure function (no dependencies) that accepts however a user might type a number (`0771234567`, `+94771234567`, `94771234567`, with spaces/dashes) and returns Text.lk's exact expected format, or `null` if it isn't a real Sri Lankan **mobile** number (rejects landlines — the digit after the `94` country code must be `7`). Duplicated client-side in `web/src/lib/phone.ts` and `mobile/src/lib/phone.ts` (same pattern as `districts.ts`) so both registration forms can validate before submitting, not just round-trip to the server to find out.
- **Phone format validation added at registration, server-side authoritative + client-side for immediate feedback.** `POST /api/users/profile` now rejects (400) a non-empty `phone` that doesn't normalize to a valid Sri Lankan mobile number — phone itself stays optional (not newly required), but a value that *is* provided must be real, since a malformed one would previously have just failed silently at SMS-send time with no indication why. The normalized (not raw-typed) value is what's stored in Firestore, so `sms.js` never has to re-guess formatting for freshly-registered accounts. `Register.tsx` (web) and `RegisterScreen.tsx` (mobile) both show the same inline error and a placeholder/hint before submitting. Verified live against the real backend: `0771234567` and `+94771234567` both normalize and save as `94771234567` (201); a landline (`0112345678`) and garbage (`12345`) both correctly reject (400 with a clear message); an empty phone still registers fine (201, `phone: null`) — confirming the field is validated, not newly required.
- **`server/src/utils/sms.js`** — `sendSmsToUser(uid, message)`, mirroring `sendNotificationToUser`'s (FCM) fail-soft philosophy exactly: missing `TEXTLK_API_TOKEN`, a user with no valid phone on file, or a non-`"success"` API response all just log and return, never throw, never block the caller's actual work. No SDK needed — it's one plain `fetch()` call, so there's no equivalent to Twilio's conditional `require()` to worry about.
- **Same three trigger points as before (unchanged from the Twilio version, only the transport changed):** `requests.js`'s `PATCH /:id/verify` and `/bulk-verify` (approve only), `deliveries.js`'s shared `notifyVictimOfDeliveryStatus()` helper (covers both the volunteer-driven `PATCH /:id/status` and the donor's `PATCH /:id/self-deliver`), and `waterLevelAlerts.js`'s `sendAreaAlert()`. Message bodies are deliberately minimal/transactional per the user's own privacy guidance while researching this provider — request ID and status only, never NIC, address, or other sensitive details in the SMS text.
- **`server/.env`** gained `TEXTLK_API_TOKEN` (a real, live token — provided directly by the user in chat, so treated as a genuine secret from the moment it arrived: written straight to `.env`, never echoed back, never placed in any client-side code) and `TEXTLK_SENDER_ID` (defaults to `"AidSystem"`).
- **Deliberately NOT live-tested against the real Text.lk API in this pass — the user's explicit instruction: "build it fully and then lets test at the very end after i say so."** The account has a limited free SMS allowance and the user wants testing to be a deliberate, single decision, not something incidentally burned through during normal build verification. `server/.env` itself carries a comment reminding whoever's in the code next not to trigger a real send (approve a request, mark delivered, etc.) without asking first — the real token being present makes every one of the three trigger points above "live" the moment they're exercised.
- **What was verified before the user's go-ahead:** the server boots cleanly with the real token present (confirms no syntax/import error, and that nothing runs at module-load time); phone validation was fully live-tested end-to-end (see above) since `POST /api/users/profile` never calls `sendSmsToUser` at all — registration and SMS-sending are genuinely separate code paths, so testing one doesn't risk the other's quota.

## Water-level area alerts

The second half of the "SMS alerts" ask: notify victims in a specific area when it's disaster-relevant — the concrete example given was "rise if water levels." Came with an explicit constraint the user settled directly rather than leaving to a default: *"lets keep both options open, approved by admin and send automatically in the admin panel with a toggle so admin can choose to automatically send or no"* — so this isn't just the auto-vs-manual choice made once at build time, it's a live admin-facing toggle.

- **`server/src/utils/waterLevelAlerts.js`** is the whole feature's brain. `STATUS_SEVERITY` ranks `normal < alert < minor_flood < major_flood`; an alert only ever fires on a genuine **escalation** (severity strictly increasing since the last check), never on de-escalation and never on staying at the same level — a station stuck at "alert" for hours doesn't spam the same victims every 10 minutes. Verified directly: re-running the check with an unchanged status produced zero new `sentAreaAlerts` entries.
- **`waterLevelAlertState`** (one doc per gauge station, doc id = slugified station name) stores just `{station, lastStatus, updatedAt}` — the minimum needed to detect "did this get worse since last time," updated on every poll regardless of whether an alert fired.
- **District matching reuses the exact same `nearestDistrict()` function** every other district-aware feature in this app already uses (stats-by-area, the requests filter, active-district declarations) — "which victims are in this district" means the same thing everywhere, not a second slightly-different implementation. A district match pulls every victim with an active (`pending`/`verified`/`in_progress`) request whose `location` resolves to that district, deduped by victim.
- **The admin toggle is a single Firestore doc** (`waterLevelAlertSettings/config`, `{autoSend: boolean}`), read fresh on every poll cycle — flipping it in the admin UI takes effect on the very next check, no restart needed. **Defaults to `false` (review-first) when the doc doesn't exist yet** — the safer of the two options is what a fresh install gets without anyone having to remember to configure it.
  - `autoSend: true` → `sendAreaAlert()` runs immediately: notifies every matching victim via the FCM helper from `## Push notifications` above, and logs one `sentAreaAlerts` entry (`source: "auto"`).
  - `autoSend: false` → a `pendingAreaAlerts` doc is created instead (nothing sent yet). `AdminWaterAlerts.tsx` (`/admin/water-alerts`) lists these with **Approve & send** / **Reject** buttons — approving calls the exact same `sendAreaAlert()` function (`source: "admin_approved"`, `approvedBy` recorded), so there's only one code path that actually sends a notification, not two slightly-different ones to keep in sync. Both approve and reject are logged to the audit log (`area_alert.approve` / `area_alert.reject`, extending `AuditLog.tsx`'s existing `ACTION_LABELS`/`describeEntry`).
- **A `setInterval` poller in `server.js`** calls `checkWaterLevelsAndAlert()` every 10 minutes, plus once immediately at startup (same warm-up pattern already used for the HDX district-boundaries cache) — this is what actually detects a rising water level; it doesn't wait for anyone to load a map. It reuses `external.js`'s existing `fetchWaterLevels()` (extracted into a standalone function and attached to the exported router as `router.fetchWaterLevels`, since Express Router instances are just functions and can carry extra properties) rather than making a second HTTP call to the same river-gauge feed the map already polls — same cache, same data, no extra load on the upstream ArcGIS service.
- **New endpoints, all admin-only**: `GET`/`PATCH /api/water-alerts/settings` (the toggle), `GET /api/water-alerts/pending`, `POST /api/water-alerts/pending/:id/approve`, `POST /api/water-alerts/pending/:id/reject`, `GET /api/water-alerts/sent` (last 50, history). No new Firestore rules needed — `AdminWaterAlerts.tsx` uses one-time `apiFetch` calls through these Express routes, not a direct client-SDK `onSnapshot` read, so nothing here is reachable by a signed-in client bypassing the API (consistent with the "lower value to make live" reasoning already used for category/broadcast history views).
- **Verified end-to-end against real infrastructure, but with one honestly-labeled synthetic input.** All 41 real river gauge stations were genuinely at `normal` status at verification time (confirmed by hitting the live feed directly) — there was no real flood to test an escalation against, the same "nothing to demo" situation already hit with GDACS and solved the same way: use real machinery, be upfront that the *trigger* was simulated. Monkey-patched the shared `fetchWaterLevels` export with one clearly-named `"TEST STATION (simulated)"` entry and ran the real `checkWaterLevelsAndAlert()`:
  - With `autoSend: false` (the default): a real `pendingAreaAlerts` doc was created, correctly matched to "Colombo" district via the real `nearestDistrict()` call. Confirmed via the real `GET /api/water-alerts/pending` HTTP route with a genuine admin ID token.
  - Approved it via the real `POST /api/water-alerts/pending/:id/approve` route — `notifiedCount: 3` (correctly found 3 real victims with active Colombo-area requests already in the database, not just the one throwaway test victim created for this check), moved to `sentAreaAlerts` with `source: "admin_approved"`.
  - Flipped `autoSend` to `true` via the real `PATCH /api/water-alerts/settings` route, then escalated the same test station further (`alert` → `major_flood`) — this time it sent immediately with **no** pending item created, confirming the branch actually depends on the live toggle value, not a cached one.
  - Re-ran the identical `major_flood` status a third time and confirmed zero new `sentAreaAlerts` entries — the no-repeat-spam guarantee holds.
  - Also click-verified `AdminWaterAlerts.tsx` itself in the browser (registered a throwaway admin through `/register`): the toggle button flips between "Auto-send: Off"/"Auto-send: On" via real clicks against the real endpoint, and the empty states render correctly.

## SOS / rescue flow

Explicitly requested as its own thing, separate from aid requests: *"'trapped,' 'missing persons,' and 'flood rescue' are life-safety emergencies needing immediate dispatch, fundamentally different urgency from 'I need food.'"* Three real decisions were confirmed with the user before building rather than guessed, since each has real security/UX consequences: **SOS requires login** (reuses the existing auth model rather than opening public unauthenticated writes), **dispatch means status tracking only** (`pending → acknowledged → in_progress → resolved`, not shoehorned into the volunteer/delivery-assignment pipeline — coordinating a rescue isn't "deliver goods"), and **any authenticated role can report one**, not just "victim" (someone could be reporting on behalf of a person they've spotted in danger).

- **`sosRequests`** is a completely separate Firestore collection from `aidRequests` — no shared schema, no priority-score algorithm, no category caps. Fields: `{reporterId, reporterName, reporterPhone, type: "trapped"|"missing_person"|"flood_rescue"|"other", peopleCount, description, location, status, createdAt, updatedAt, acknowledgedAt, resolvedAt}`.
- **`POST /api/sos`** (any authed role) — deliberately minimal required fields (`type` + `location` only; `peopleCount`/`description` optional) so submitting is as close to one tap as this app gets. Every admin is pushed an FCM notification immediately (`sendNotificationToUser` from `## Push notifications` above, fanned out to every `role: "admin"` user) — this is the one place in the app where "someone sees this in seconds" is the actual requirement, not "eventually shows up in a queue."
- **`PATCH /api/sos/:id/status`** (admin) — the four-stage status flow, stamping `acknowledgedAt`/`resolvedAt` once (same "set on first transition, never overwritten" pattern as `aidRequests.verifiedAt`). Notifies the original reporter on every status change too, so they know help is coming without refreshing anything. Logged to the audit log (`sos.status_update`, extending `AuditLog.tsx`).
- **`SosButton.tsx`** — a persistent floating red button rendered in `DashboardLayout.tsx` for every logged-in role, opening a single-screen modal (not a multi-step wizard, which would add friction, not remove it): 4 big type buttons, geolocation auto-captured the instant the modal opens (not gated behind a second "capture location" tap), optional people-count and description fields, one submit button. Fully translated (EN/SI/TA) since this is exactly the kind of high-stakes, high-equity surface the i18n work has prioritized elsewhere.

## Delivery chat + consent-gated contact sharing

Requested directly: a chat between whichever two parties are actually coordinating a specific delivery, plus an explicit opt-in to reveal real name/phone between them. Two design decisions were confirmed with the user before building rather than guessed, since both have real privacy consequences: **mutual consent** (neither side's real name/phone is revealed until BOTH have agreed — not one-sided sharing), and **active-delivery-only availability** (chat opens once the two parties are actually linked, and locks — read-only — once the delivery is confirmed, rather than staying open indefinitely).

- **Which two parties, derived from the existing delivery model, not a new relationship:** a volunteer-delivery delivery gets **two independent chats** — donor↔volunteer (coordinate pickup) and volunteer↔victim (coordinate dropoff) — since the volunteer is the actual intermediary and donor/victim never interact directly in that flow. A self-delivery delivery gets **one** chat — donor↔victim directly — since there's no volunteer in that flow. Never a three-way room.
- **`deliveryChats`** Firestore collection, one doc per (delivery, pair): doc id is the deterministic `${deliveryId}_${pairKey}` (`pairKey` ∈ `donor_volunteer`/`volunteer_victim`/`donor_victim`) — deliberately deterministic so the frontend can construct the id directly from data it already has (a delivery's own id + method), with no extra lookup round trip before opening a chat. Fields: `{deliveryId, requestId, donationId, pairKey, partyAId, partyARole, partyBId, partyBRole, consentA, consentB, contactRevealed, status: "active"|"locked", createdAt, updatedAt}`. **Real name/phone are deliberately never stored on this doc** — the chat only ever identifies the other party by role (e.g. "volunteer") until `contactRevealed` is true, at which point the name/phone are looked up fresh from `users`, not frozen at chat-creation time.
- **`chatMessages`** — top-level collection (not a subcollection), same convention as `caseNotes`: `{chatId, senderId, senderRole, text, createdAt}`, queried by `chatId` and sorted by `createdAt` in JS rather than `orderBy` in the query, avoiding the same composite-index dependency already documented under "Internal case notes."
- **`server/src/utils/deliveryChats.js`** is the creation/locking logic, called from exactly three places: `deliveries.js`'s `PATCH /:id/accept` (creates both volunteer-delivery chats — **at accept, not at assignment/pending_acceptance**, since before a volunteer actually commits there's no real counterpart yet and they could still be swapped for someone else), `donations.js`'s `POST /:id/match` self-delivery branch (creates the donor↔victim chat immediately, since self-delivery has no accept step), and `deliveries.js`'s `POST /:id/confirm` (locks every chat tied to that delivery). All three fail soft — a chat failing to create or lock never blocks the actual accept/match/confirm action it's attached to.
- **`server/src/routes/chats.js`** — `GET /mine` (every chat the caller is a participant in, two queries merged in JS since Firestore can't OR across two different fields), `POST /:chatId/messages` (blocked once locked, notifies the other party via **FCM only, deliberately not SMS** — a chat can generate many messages and this project's Text.lk quota is limited and reserved for the handful of already-wired higher-value trigger points), `PATCH /:chatId/consent` (sets the caller's own flag; no revoke, same one-way-consent convention as everything else in this app; flips `contactRevealed` and notifies both sides once both flags are true), `GET /:chatId/contact` (returns the *other* party's name+phone, but only once `contactRevealed` is true — this is the one place in the app that hands one user another user's PII, and it's deliberately narrow: two fields, gated on mutual consent, resolved fresh from `users` rather than trusting a client-supplied value).
- **New Firestore rule block for `deliveryChats`/`chatMessages`** — both need a live listener (`ChatModal.tsx` subscribes to the chat doc for status/consent state, and to `chatMessages` for the message list), so these rules are load-bearing, not just a safety net. Read allowed only for the two named participants (or admin); **all writes blocked at the rules level for every role, including admin** — Admin SDK bypasses rules entirely, so the Express API still writes fine; this just ensures a client can never bypass the locked/mutual-consent business logic with a direct write. `chatMessages`' rule does a cross-document `get()` on the parent `deliveryChats` doc to check participancy, same pattern already used by `isOwningDonor()` in this same rules file. **Deployed** via `firebase deploy --only firestore:rules`, confirmed with the user first.
- **`ChatModal.tsx`** (new shared component, same modal pattern as `CaseNotesModal.tsx`/`QrScanModal.tsx`) — live `onSnapshot` on both the chat doc and its messages, a "Share my name & phone" button that disappears once *my* consent is given (replaced by "waiting for the other side" until both have agreed, then the real name/phone appear in the header), and a message composer that hides entirely once the chat is locked (read-only history instead). Opened from a "💬" button wherever a delivery is chattable: `VolunteerDeliveries.tsx` (two buttons per delivery — donor and victim), `DonorMyDonations.tsx` (one button, labeled by delivery method), `VictimMyRequests.tsx` (one button per item, translated — new `victimMyRequests.chatWith{Donor,Volunteer}` i18n keys in all three locale files, matching this page's existing translated-page status). All three gate the button on the delivery status actually being chattable (`accepted`/`picked_up`/`delivered`/`confirmed` — not `pending_acceptance` or `rejected`).
- **Verified end-to-end via real HTTP calls** (temp victim/donor/volunteer/admin, real Firebase ID tokens, a full run of both the volunteer-delivery and self-delivery paths): confirmed no chat exists before a volunteer accepts, both chats appear correctly the instant they accept; `GET /mine` correctly lists both for the volunteer; a message sent by the donor lands in Firestore with the right sender/role; a non-participant (the victim, on the donor↔volunteer chat) is correctly rejected with 403; one-sided consent correctly leaves `contactRevealed: false` and `GET /contact` returns `{revealed: false}`; consenting on both sides correctly flips it true and the other party's *real* name and phone come back; confirming the delivery correctly locks both chats, and a further send attempt is correctly rejected with a clear "locked" error; the self-delivery path correctly creates its one donor↔victim chat immediately at match time, with no accept step. All test accounts and data deleted afterward.
- **Also verified live in the browser, both before and after the rules deploy** — this caught something the API-only tests couldn't: before deploying, opening `ChatModal.tsx` for real (throwaway volunteer account, accepted delivery, clicked the "💬 Donor" button) hung forever on "Loading..." with a real `permission-denied` in the console, confirming the rules genuinely are load-bearing and not just a paper safety net. After `firebase deploy --only firestore:rules`, the identical flow — accept, open chat, send a message — worked correctly end-to-end: the modal loaded immediately and the sent message appeared live via the real `onSnapshot` listener, not a page reload. Test accounts and data deleted afterward.
- **A real mistake made while testing this, corrected and disclosed rather than glossed over:** the test script generated random-but-validly-formatted Sri Lankan phone numbers for every test account, including the victim — which meant the existing SMS trigger points (`verify`, `picked_up`, `delivered`) fired real Text.lk sends to a nonexistent number during this test run, burning real SMS credits from this project's limited quota. This directly conflicts with the user's own standing instruction to treat SMS testing as a deliberate, separate decision, not something incidentally triggered by testing an unrelated feature. **Lesson for future sessions: any test account whose flow touches `verify`/`picked_up`/`delivered`/`self-deliver` must have `phone: null` (or an intentionally invalid, unnormalizable value) unless SMS testing is the explicit goal** — a syntactically-valid fake number is not safe just because it's fake.

## QR-code delivery confirmation

Replaces a same-device "Confirm receipt" button tap — the victim now has to physically scan a code shown by whoever has the goods, which is harder to fake.

- When a delivery reaches `delivered` (via `PATCH /:id/status` or `PATCH /:id/self-deliver`), the backend generates a random `confirmToken` (`crypto.randomBytes(16)`) and stores it on the delivery.
- `DeliveryQrCode.tsx` renders that token + the delivery id as a QR (`qrcode.react`) on `VolunteerDeliveries.tsx` and `DonorMyDonations.tsx` (self-delivery) — shown to whoever has physical custody of the goods.
- `QrScanModal.tsx` opens the victim's camera (`html5-qrcode`) from `VictimMyRequests.tsx`'s "Scan to confirm" button, decodes `{deliveryId, token}`, and calls `POST /:id/confirm` with that token.
- **`POST /api/deliveries/:id/confirm` now requires the body's `token` to match `delivery.confirmToken`** in addition to the existing victim-ownership check — a wrong or missing token gets a 403, verified live.
- `GET /api/deliveries/by-request/:requestId` (the victim's own delivery list) deliberately **strips `confirmToken` out of the response** — the victim's client is never handed the token directly, only whoever generates the QR sees it. Don't add it back there even if it seems convenient.
- Camera access needs a secure context (HTTPS) in production — works on `localhost` for dev without issue, but note this when deployment planning starts.

**Note on live location:** `currentLocation` today is only a snapshot captured once per status-change button click, not continuous tracking. True "PickMe-style" live tracking (needed for turn-by-turn navigation) needs `navigator.geolocation.watchPosition` streaming into Firestore periodically, with the victim/admin side using a real-time Firestore listener instead of the current polling `apiFetch` pattern. Bigger lift than it sounds — its own task when navigation gets built, not a small addition.

### Real district boundary polygons (HDX COD-AB)

A follow-on request: replace the centroid-circle approximation on the public severity map with real district polygons, from HDX's official COD-AB (Common Operational Dataset — Administrative Boundaries) dataset — Survey-Department-of-Sri-Lanka-sourced, OCHA-vetted, admin levels 0-4 (country → 9 provinces → 25 districts → 339 DS divisions → 14,043 GN divisions). Admin-2 (25 districts) is what matches this project's existing district granularity.

- **The specific "live ArcGIS geoservice" the user asked for is genuinely dead — verified, not assumed.** `codgis.itos.uga.edu` and `gistmaps.itos.uga.edu` (the documented COD_External ArcGIS REST hosts) return **NXDOMAIN from both Google's (8.8.8.8) and Cloudflare's (1.1.1.1) public DNS** — not a local network fluke, a real global DNS failure. ITOS (Information Technology Outreach Services, University of Georgia — who ran this service) has itself been reorganized: their old site now 301-redirects into UGA's Carl Vinson Institute of Government. Flagged to the user directly (via AskUserQuestion) rather than silently substituting, same pattern as the DMC and GDACS findings above.
- **What's actually reachable: HDX's own file CDN.** `data.humdata.org`'s CKAN API (confirmed working, `curl`-tested directly) serves the same official COD-AB dataset as a downloadable resource, redirecting to an S3-backed URL. Downloaded and inspected directly: `lka_admin2.geojson` has exactly 25 features, real Survey-Department polygons, and — a genuine bonus — English/Sinhala/Tamil district name fields already included (`adm2_name`/`adm2_name1`/`adm2_name2`), on top of province, p-code, and area.
- **The raw file is too heavy to serve to a browser as-is** (~20MB for just the admin-2 layer — precision-grade GIS data, not web-map-ready) and the full zip (all 5 admin levels + lines/points) is ~130MB. `server/src/routes/external.js`'s `fetchDistrictBoundaries()` downloads the zip, extracts only `lka_admin2.geojson` via `adm-zip`, and simplifies it with `@turf/simplify` (Douglas-Peucker, `tolerance: 0.002`, `highQuality: true`) — cuts it from ~20MB / hundreds of thousands of vertices down to **~280KB / 6,749 points** across all 25 districts, visually indistinguishable at web-map zoom levels. Response fields are trimmed/renamed to `{district, districtSi, districtTa, province, pcode, areaSqKm}` per feature.
- **`GET /api/external/district-boundaries`** — public, cached 24h (`DISTRICT_BOUNDARIES_CACHE_TTL_MS`, the longest TTL of any external feed here — district boundaries don't change during a dissertation's lifetime). Fails soft to `null`, same as every other external feed.
- **The cold-cache download alone takes 1-2.5+ minutes** (133MB over a real network) — far too slow to happen inside a page load. Two mitigations, both in `external.js`: (1) the cache is **warmed once at server startup** — a fire-and-forget `getCached(...)` call at module load, so by the time a real user (or a viva examiner) opens the map, the fetch has almost certainly already completed in the background; (2) the frontend (`AreaSeverityMap.tsx`) fetches boundaries in a **separate, non-blocking `useEffect`** that never gates the map's initial render — if `boundaries` is still `null` (cold cache mid-warm-up, or the fetch failed), the map **falls back to the original centroid-circle rendering** exactly as before, so the feature can only improve the map, never break it.
- `AreaSeverityMap.tsx` renders district polygons via react-leaflet's `<GeoJSON>` (colored via a `style` function that looks up each polygon's district name against the existing `/api/stats/by-area` response — same severity levels, same color values, just filled into a real shape instead of a circle) with `onEachFeature` binding the same popup content as before. Districts with **no active requests get a distinct "No activity" gray** (`#9ca3af`, low fill opacity) rather than being invisible or reusing the "low" green — added a 4th legend entry and a new `severityMap.noActivity` i18n key (EN/SI/TA) for it, since without it a mostly-quiet demo dataset would render 24 of 25 districts as blank space.
- Verified live: `curl`'d the endpoint directly (25 features, correct trimmed properties, Sinhala/Tamil names intact); confirmed in-browser via DOM inspection that all 25 `<path>` elements render with the correct fill (1 district colored by its real active-request level, 24 in the "no activity" gray); clicked the colored district's popup and confirmed accurate content ("Colombo — 3 active requests — High need") rendered over the district's actual non-circular shape, not a circle; confirmed the same shared component still works correctly on both the Landing page's embedded preview and the full `/severity-map` page, and that the "River Levels" tab (still `CircleMarker`-based, unaffected by this change) continues to work.

### Sidebar overlap bug (fixed)

User-reported, from a screenshot: on `/dashboard` (admin role, which has the longest nav list — 13 items), the bottom-left profile name, role label, and "Log out" button visually overlapped the last couple of nav links ("Audit Log", "Volunteer Workload").

- **Root cause**: `DashboardLayout.tsx`'s `<aside>` had no height/flex structure — `<nav>` rendered in normal flow with no cap, and the profile/logout block was `absolute bottom-0`, anchored to the `<aside>`'s own box height rather than pushed below the nav content. Once the admin role's nav list (12 items + the always-present "Overview" link) grew taller than the aside's rendered height, the absolutely-positioned footer sat on top of the overflowing tail end of the nav instead of after it.
- **Fix**: `<aside>` is now `flex w-64 shrink-0 flex-col`; `<nav>` is `flex-1 flex-col gap-1 overflow-y-auto` (grows to fill remaining space, scrolls internally if a role's list is ever too tall for the viewport); the profile/logout block dropped `absolute`/`bottom-0`/the redundant `w-64` and is just `shrink-0` in normal flow. This guarantees the footer always renders immediately after the nav with zero overlap, for any nav length, on any role.
- **An earlier version of this fix also added `sticky top-0 h-screen self-start`** (to pin the sidebar to the viewport and let only the nav scroll) — reverted after live testing showed it caused a *different* overflow: `h-screen` is 100vh measured from wherever the aside sits in normal flow, and the real "Active emergency declared in: Colombo" district banner (a persistent bar, not a one-time dismissible one — see "Active emergency districts") pushes the whole layout down ~49px, so a full-100vh sidebar then poked ~49px past the bottom of the viewport. Simplest robust fix: don't pin the sidebar to the viewport at all — let it stretch naturally to match the row's height (its original, pre-bug behavior), with `flex-1 overflow-y-auto` on the nav as the safety net if content ever exceeds that height. No viewport-offset edge case, and the overlap is still structurally impossible.
- **Also removed while fixing this**: the admin `NAV_BY_ROLE` array had a redundant last entry, `{ labelKey: "nav.dashboard", path: "/dashboard" }` ("Dashboard") — pointing to the exact same route as the always-rendered "Overview" link above it (confirmed via grep as the only reference to `nav.dashboard` anywhere in the codebase, and via `en.json` that `nav.overview`/`nav.dashboard` are two different label strings for one destination). Removing it also shortens the admin nav list by one item, directly reducing how easily it overflows a short viewport in the first place.
- Verified live: registered a throwaway admin account through the real `/register` UI, measured the sidebar's actual DOM geometry via `getBoundingClientRect()` on `/dashboard` (13 nav links, all visible, no duplicate "Dashboard" entry) — nav's bottom edge and the footer block's top edge sit at the exact same pixel with zero overlap, both before and after re-checking with the real "Colombo" active-district banner pushing the layout down. Deleted the test account (Firestore doc + Firebase Auth user) afterward.
- Checked for the same class of bug elsewhere per the user's "fix all such issues" instruction: grepped `web/src` for other `absolute` + `bottom-0` combinations — none found, this was the only instance. ### SOS modal rendering behind the Leaflet map (fixed)

Also user-reported, from a screenshot: opening the floating SOS button's modal on `/admin/sos` showed the Leaflet map's zoom controls and tiles rendered *on top of* the bottom portion of the modal, cutting off its text.

- **Root cause**: `SosButton.tsx`'s modal overlay used Tailwind's `z-50` (`z-index: 50`), but Leaflet's own CSS assigns much higher **raw** z-index values to its internal panes and controls — `.leaflet-pane` at 400, `.leaflet-top`/`.leaflet-bottom` (zoom controls etc.) at 1000 — which aren't on Tailwind's scale and easily outrank an app z-index chosen without accounting for them. - **Fix**: bumped the modal overlay to `z-[1200]` (comfortably above Leaflet's 1000 ceiling). Applied the identical fix to every other component sharing this exact `fixed inset-0 z-50` full-screen-overlay pattern — `QrScanModal.tsx`, `CaseNotesModal.tsx` — plus `NotificationSetup.tsx`'s corner toast (`fixed bottom-4 right-4 z-50`), even though none of those three are currently opened on a page with a map, since they're the same pattern and would hit the identical bug the moment one ever is.
- Verified live: registered a throwaway admin, opened `/admin/sos` (has a Leaflet map) and triggered the SOS modal, then used `document.elementFromPoint()` at the modal's own center to confirm the element actually painted there is the modal's content, not the map — confirmed `overlayZIndex: "1200"` vs `leafletPaneZIndex: "400"` and `isModalOnTop: true`. Deleted the test account afterward.

### Push notifications on mobile — code complete, needs a custom dev build to actually test

**A real, project-changing discovery while scoping this: Expo Go dropped support for remote push notifications entirely, around SDK 53**, due to Apple/Google policy changes — this has nothing to do with this app's code, it's a platform-wide Expo change. Testing push notifications now requires a **custom development build** (`eas build` or local `expo prebuild`), not the plain Expo Go app this whole mobile build has been tested with up to this point. Flagged directly to the user rather than silently building unverifiable code; **the user chose to set up a custom dev build now** rather than defer push notifications or ship the code untested.

- **`mobile/src/lib/notifications.ts`** — mirrors `web/src/lib/notifications.ts`'s contract exactly (`requestAndRegisterPushToken()`, `onForegroundMessage()`), registering against the *same* `POST /api/users/fcm-token` endpoint with **zero server-side changes**. The key design choice: uses `expo-notifications`'s `getDevicePushTokenAsync()` — the **raw native FCM registration token** on Android — rather than an Expo push token. This is the same *kind* of token web already sends via the Firebase JS SDK's `getToken()`, so the backend's existing `admin.messaging().sendEachForMulticast()` call keeps working unmodified; switching to Expo's own push token would have required a second, divergent send path server-side.

## Turn-by-turn volunteer navigation ("like PickMe") — built (web)

**The Google Maps blocker is resolved: the user supplied a real API key** (Google Cloud Console, project has Maps JavaScript API, Maps SDK for Android, Places API, Geocoding API, and Routes API enabled). Asked the user which to build first, web navigation or mobile maps — **they chose web navigation first**; mobile maps stays deferred (see its own entry below).

- **`server/src/routes/deliveries.js`** gained `GET /:id/navigation-info` (volunteer-only, ownership-checked against `delivery.volunteerId`) — combines `donation.location` (pickup) and the linked `aidRequest.location` (dropoff) into one response, `{id, status, category, pickupLocation, dropoffLocation}`. A volunteer has no other endpoint that would let them read either the donation or the request document directly (both are admin/donor/victim-scoped elsewhere), so this is a new minimal-surface endpoint rather than widening an existing one.
- **`web/src/pages/VolunteerNavigation.tsx`** (`/deliveries/:id/navigate`) — uses `@react-google-maps/api` (`useJsApiLoader`, `GoogleMap`, `Polyline`, `MarkerF`). Destination is derived from the delivery's own status, not a separate field: `status === "accepted"` → head to the **pickup** (donation location, not yet collected); `status === "picked_up"` → head to the **dropoff** (victim's request location). Volunteer's own position is a one-off `navigator.geolocation.getCurrentPosition()` snapshot (same pattern as everywhere else in this app) with a "Refresh my location" button to recompute, **not** continuous tracking — that's the separate live-location-tracking rework already flagged elsewhere in this file, deliberately not bundled into this pass.
- **Deliberately built against Routes API's REST endpoint directly (`POST https://routes.googleapis.com/directions/v2:computeRoutes`), not the legacy `google.maps.DirectionsService` class, and not `@react-google-maps/api`'s `DirectionsRenderer`.** First version used `DirectionsService` (the obvious/default choice with this library) and hit `REQUEST_DENIED` on the very first live test — turned out `DirectionsService` calls the **legacy Directions API**, a separate product from Routes API despite the similar name, and the user's initial API list had Routes API enabled but not Directions API. **The user's explicit direction on fixing this**: don't enable Directions API at all — Routes API is Google's current/recommended product for anything started in 2026, so rewrite to call it directly instead. `computeRoute()` in `VolunteerNavigation.tsx` does the `fetch()` call itself (confirmed Routes API sends proper CORS headers for direct browser calls, unlike the older Directions/Places REST endpoints which need a server-side proxy), decodes the returned encoded polyline via `google.maps.geometry.encoding.decodePath()` (needs `libraries: ["geometry"]` passed to `useJsApiLoader`, as a module-level stable array reference — a new array literal every render makes `@react-google-maps/api` reload the script), and renders it with a plain `<Polyline>`.
- **Cost-conscious field mask, confirmed with the user rather than assumed.** Routes API bills per-step turn-by-turn text instructions (`routes.legs.steps` + `navigationInstruction`) at a pricier tier than a basic route (polyline + total distance/duration only). Asked the user directly given they'd just said "don't overuse the free usage, I don't want to pay" — **they chose the basic/cheapest tier**, so the `X-Goog-FieldMask` header requests only `routes.duration,routes.distanceMeters,routes.polyline.encodedPolyline`. This is also why there's no numbered turn-by-turn instructions list in the UI anymore (an earlier version, built against the wrong API, had one) — just the drawn route line plus a "17.0 km · about 44 min" summary line. Revisit this field mask (and the cost tradeoff) if per-step instructions are ever wanted later.
- **Billing still required regardless of which Maps product is used — this doesn't go away by avoiding Directions API.** Hit `REQUEST_DENIED` a second time after the API-mismatch fix, this time with an explicit `error_message`: `"You must enable Billing on the Google Cloud Project..."` — confirmed via a direct `curl` against the Directions REST endpoint (isolating the failure from any app code) that the *project itself* had no billing account linked, a separate requirement from which specific API is enabled. Flagged directly to the user rather than assuming Routes API would sidestep this (it wouldn't have — billing is a project-level Google Cloud Platform requirement for essentially every Maps Platform product, Routes API included) — they enabled billing, then this section's fix was verified working end-to-end.
- **`web/src/pages/VolunteerDeliveries.tsx`** gained a "Navigate" link next to the status badge, shown only while a delivery is `accepted` or `picked_up` (the two statuses that actually have a "go somewhere" destination — `pending_acceptance` has nothing to navigate to yet, `delivered`/`confirmed` are already done).
- **A real bug hit and fixed early on, not just a config issue: `@react-google-maps/api`'s class-based `<Marker>` silently failed to render anything under `React.StrictMode`** (which `main.tsx` has always had enabled) — the marker constructor ran (confirmed via Google's own "Marker is deprecated" console warning firing), but no pin ever appeared in the DOM, no error either. This is a known StrictMode/double-invoke interaction with the library's legacy class-component wrapper. Fixed by switching to `MarkerF`, the function-component variant the library ships specifically for this.
- Verified live end-to-end via a seeded test volunteer + request + donation + delivery (Admin SDK, real HTTP login through the actual `/login` UI, mocked `navigator.geolocation.getCurrentPosition` in-page since this browser-automation environment can't grant real OS-level location permission — same documented limitation noted elsewhere in this file for QR camera scanning): confirmed the pickup/dropoff marker switches correctly with delivery status, confirmed real Google Maps tiles render, and — the part that actually needed the Routes API rewrite plus billing fix to work — confirmed the route **actually renders as a real orange polyline following streets on the map**, with the correct "17.0 km · about 44 min" summary text, not just that the request was sent without erroring.

## Concurrent-load testing

Directly answers a gap the dissertation itself acknowledges rather than glosses over: formal evaluation at high concurrent user volume, alongside structured cross-role usability evaluation, had been outstanding. **The two are genuinely different things and were not conflated**: usability evaluation (SUS scores, facilitator-guided scenarios — see `evaluation/`) needs real human participants and can't be simulated or faked; concurrent-load testing is pure engineering and can be run directly against the real system, which is what this section covers.

- **`server/load-test.js`** (kept in the repo, not deleted, as evaluation-chapter evidence/reproducibility material) — creates real throwaway Firebase accounts (30 victims, 30 donors, 15 volunteers, 1 admin) via the Admin SDK, gets real ID tokens via the Identity Toolkit REST API (same technique used throughout this project's manual testing history), then fires genuinely concurrent (`Promise.all`, not sequential) requests at the real Express + Firestore backend across five phases: concurrent request submission, concurrent admin approval, concurrent donation registration, concurrent donation-matching (the real race-condition probe, see below), concurrent volunteer accept, and a 50-request concurrent read burst. Reports min/avg/p95/max latency and success/failure counts per phase, then deletes every trace of itself (Firestore docs + Auth accounts).
- **The race-condition probe (Phase 3) is the highest-value check, not just a performance number.** 30 donations all needing to match against the same pool of 30 pending "water" request items, fired at `POST /api/donations/:id/match` simultaneously — `donations.js`'s match logic reads candidates then writes without a Firestore transaction, so this is exactly the scenario where two concurrent match calls could both read the same "best" request before either write lands, and both try to claim the same item. **Verified clean**: a post-run integrity check (counting how many times each `donationId` appears across all request items) found zero double-matched items across the run. Worth re-running this specific check if the matching logic in `donations.js` is ever touched.
- **A real bug found and fixed, not just numbers collected**: the first run showed `/api/stats` and `/api/stats/by-area` doing a full, uncached collection scan on every call — Phase 5's 50-concurrent-read burst had a p95 of ~11s against a min of 18ms (the fast ones were cache hits on `/api/external/water-levels`, the slow ones were these two). Added caching via the existing `utils/cache.js` (30s TTL, `STATS_CACHE_TTL_MS`) — but the very next run got **worse** (p95 ~25s), which surfaced a second, more interesting bug: **`getCached()` itself had no protection against concurrent cache misses.** It cached the *resolved value*, not the in-flight promise, so 50 simultaneous requests hitting a cold cache all independently triggered their own full collection scan — a classic cache-stampede, worse than no caching at all under this exact load pattern. Fixed by storing the in-flight *promise* in the cache map synchronously (before the first `await`), so concurrent callers past the first share one fetch instead of each starting their own — re-verified: p95 dropped to ~2.4s, better than the original uncached baseline. **This fix is in shared infrastructure** (`utils/cache.js`), so it also protects every other endpoint that uses it (`/api/external/alerts`, `/water-levels`, `/gdacs`, `/district-boundaries`, `/earthquakes`, `/weather`) from the same stampede risk under concurrent load, not just the two stats endpoints that surfaced it.
- **Honest inconsistency, not smoothed over**: a third consecutive run (same script, run back-to-back within a few minutes) showed Phases 3 and 4 running much slower than the first two runs (Phase 4 avg jumped to ~59s). Neither of those phases touches the code that changed (`donations.js`/`deliveries.js` match/accept logic, untouched by the cache fix), so this wasn't a regression — almost certainly Firebase Auth/Firestore rate-limiting or quota backoff after three rapid runs each creating and deleting 76 accounts in quick succession. Documented rather than hidden, since a dissertation evaluation chapter reporting only the best run would be less credible than one that shows the full picture and reasons about the outlier correctly.
- Verified: all three runs, 100% request success rate across every phase (zero HTTP-level failures against the real backend under concurrency); the integrity check passed on every run; the cache-stampede fix specifically confirmed via before/after re-run, not assumed.

## Flood risk forecast (ML)

Requested by the user's dissertation supervisor: predict when/where floods are likely to happen from historical data and climate. This directly reverses the dissertation's own "No AI/ML" scope cut (see above) — flagged to the user via `AskUserQuestion` before building anything, offering three real options (a no-ML seasonal+trend heuristic, a real-historical-data statistical model, or true ML) with their tradeoffs stated plainly; **the user picked true ML explicitly**, so this is a deliberate, confirmed scope reversal, not scope creep.

- **Real ground-truth data, not synthetic — found by the same "verify before building" discipline as every other external source in this file.** Two genuinely real, free, verified-live data sources, both cited directly in the model's own output and in the UI caption:
  1. **UNDRR's DesInventar Sri Lanka disaster database** (`https://www.desinventar.net/DesInventar/download/DI_export_lka.zip`) — a real, public, ~18MB export (confirmed by downloading and parsing it, not assumed from documentation) containing **130,140 individual historical disaster incident records for Sri Lanka**, each with district, date (year/month/day), hazard type, and impact fields. Filtered to flood-type hazards (`FLOOD`, `FLASH FLOOD`, `URBAN FLOOD`, `CYCLONE & FLOOD`) → **8,182 real flood incidents, 1981-2020**, trimmed to `{district, year, month, day, eventType}` and checked into the repo as `server/src/data/desinventar-flood-records.json` (~600KB) rather than re-downloading/re-parsing the full 1.2GB decompressed XML on every training run.
  2. **NASA POWER's free Daily API** (`https://power.larc.nasa.gov/api/temporal/daily/point`) — real historical daily precipitation (MERRA2/GEOS-IT reanalysis), no API key needed, confirmed reachable and returning real data by direct query. Data starts 1981-01-01, which is why training is clipped to 1981-2020 (DesInventar's own records go back to 1974, but there's no rainfall data to pair with anything before 1981). Also used live at request time (see below) — it has only a ~2-3 day publishing lag, confirmed directly.
- **A real district-name mismatch caught and fixed, same class of bug as `RESERVOIR_DISTRICT_ALIASES`**: DesInventar spells it "Moneragala," this project (matching the Survey Department spelling used everywhere else) uses "Monaragala" — `DESINVENTAR_DISTRICT_ALIASES` in the training script fixes this explicitly rather than silently dropping those records.
- **`server/scripts/train-flood-risk-model.js`** — the offline (re-runnable, `npm run train-flood-model` from `server/`) training script. Builds one training sample per (district × year × month) for 1981-2020 (25 districts × 40 years × 12 months = 12,000 samples), label = 1 if DesInventar recorded a flood-type incident in that district-month. Features: that month's total rainfall (mm), the 30 days of rainfall immediately preceding the month (antecedent soil-saturation signal — a standard real flood-risk indicator, not invented for this), month encoded as sin/cos (captures the dual-monsoon seasonality without a hard month boundary), and the district's own overall historical flood frequency (captures real geographic flood-proneness — e.g. Ratnapura sits at a river confluence and floods far more than the arid north — at the cost of soft data leakage, since each district's feature is partly derived from its own labels; acceptable and disclosed for a dissertation-scope model, not held out to a separate test set).
- **A genuine logistic regression, hand-rolled in plain JS (gradient descent, L2-regularized), not a pulled-in ML dependency** — 4-6 features is small enough that a from-scratch trainer is more auditable for a dissertation than an opaque library call, consistent with this project's "don't add a dependency you don't need" convention.
- **Honestly evaluated, not oversold.** Raw 0.5-threshold accuracy (90.3%) is barely above the "always predict no flood" baseline (90.2%) — meaningless here because only ~9.8% of samples are positive. The metric that actually matters for a risk *ranking* — top-decile precision — shows real signal: **the model's riskiest-predicted 10% of district-months are ~3.8x more likely to have had a real historical flood than a random month** (37.6% precision vs. 9.8% base rate). Both numbers are written into the trained model file and surfaced directly in the UI caption on both map pages — the user sees the same honest number a reviewer would.
- **`server/src/utils/floodPrediction.js`** — the runtime serving module. Loads the already-trained `server/src/data/flood-risk-model.json` once (no retraining at request time) and, for the *current* calendar month, computes live features per district: a live NASA POWER call for that district's centroid, this month's rainfall-so-far, and the 30 days before this month started.
  - **A real edge case caught and fixed during verification, not left as a silent flaw**: NASA POWER's ~2-3 day publishing lag means early in any month, zero days of the current month have data yet — without a fix, the model's most heavily-weighted feature would default to "zero rain this month," flattening every district to "low risk" regardless of real recent conditions (this genuinely happened on first test, verified before fixing, not assumed). Fixed with a fallback: when no current-month days are observed yet, project the full-month rainfall estimate from the average of the most recent 10 fully-reported days instead of defaulting to zero. Re-verified after the fix: the ranking correctly reflected real active heavy rain in the southwest at the time (see below).
  - Risk levels: `low` (≤15%), `moderate` (≤30%), `elevated` (≤50%), `high` (>50%) — thresholds chosen to spread the output usefully across the model's real probability range, not derived from any external standard.
- **`GET /api/external/flood-risk`** (public, cached 6h — a full refresh means 25 sequential live NASA POWER calls, expensive to do per-request) — returns `{available, model: {trainedAt, trainingWindow, topDecilePrecision, baseRate, sources}, districts: [{district, lat, lng, month, probability, riskLevel, basis}]}`. Fails soft to `{available: false, districts: []}` if the model file is missing (e.g. before the training script has ever been run).
- **`POST /api/external/flood-risk/retrain`** (admin only) — re-runs the exact same training pipeline live, so an admin doesn't need shell access to refresh the model when new DesInventar records get added. The training logic itself was pulled out of the CLI script into a shared `server/src/utils/trainFloodRiskModel.js` (`trainFloodRiskModel({onProgress})`) so `scripts/train-flood-risk-model.js` and this route call the exact same code, not two copies that could drift. Reloads the in-memory model and busts the `flood-risk` cache entry immediately after writing, so the very next `GET /flood-risk` reflects the fresh model rather than serving a stale cached response for up to 6 more hours. Logs `flood_model.retrain` to the audit log (sample count + top-decile precision), extending `AuditLog.tsx`'s `ACTION_LABELS`/`describeEntry`. Surfaced as a "Retrain model now" button next to the model's "Trained {date}" timestamp on `SituationMap.tsx`'s Flood Risk Forecast tab (admin-only page, so no extra role gating needed in the component itself) — the public map has no equivalent control.
  - **A real dev-environment bug found while verifying this, not a production issue**: the first live test of the button showed the browser reporting "Failed to fetch" every time, which looked like the endpoint was broken — but the model file's `trainedAt` timestamp had genuinely updated to the exact second of the click, both times, proving the training itself completed successfully server-side. Root cause: `nodemon` (used only by `npm run dev`, not `npm start`) watches the whole `server/` directory by default, and the training pipeline writes `src/data/flood-risk-model.json` — the moment that write lands, nodemon restarts the dev server, killing the in-flight HTTP response before Express can send it back. This never happens in production (`npm start` doesn't use nodemon) but would hit every single local dev-time test of this button otherwise. Fixed with a `nodemonConfig.ignore: ["src/data/*.json"]` entry in `server/package.json` — data artifacts written by the app shouldn't trigger an app restart, only a model reload, which the route already does explicitly via `reloadModel()`.
  - Verified end-to-end via real HTTP calls with a genuine admin ID token (temp account, Identity Toolkit REST sign-in): the retrain endpoint correctly re-fetched all 25 districts' NASA POWER history, retrained, and produced a fresh `trainedAt`/`topDecilePrecision`; a correctly-shaped `flood_model.retrain` audit entry was recorded each time and rendered on `/admin/audit-log` with a human-readable detail line ("12000 samples, 3.8x baseline top-decile precision"). This first verification pass was run against the *old*, not-yet-restarted server, so it proved the training/audit-logging logic was correct but still hit the "Failed to fetch" symptom on the HTTP response itself — expected, since the nodemon fix needs a restart to take effect (nodemon only reads its ignore config at its own startup, so killing just the app child process nodemon manages isn't enough — the nodemon process itself has to be stopped and relaunched).
  - **Restarted and re-verified clean, closing the loop.** Found the actual process holding port 5000 (`Get-CimInstance Win32_Process`, since PowerShell was needed to see the parent/child relationship `netstat` alone doesn't show): a plain `node src/server.js` child (PID 8580) under a `nodemon.js src/server.js` parent (PID 9336). ## Privacy and security notes — non-negotiable constraints

- **NIC number and home address are sensitive PII.** Never expose either in: the public transparency dashboard, the public severity map, any API response reachable without `requireRole("admin")` or the record's own owner, or any client-side console log left in committed code. In any admin list view, consider masking (e.g. show only the last 4 digits of the NIC) with full value visible only on a dedicated detail view. Firestore rules must restrict the `users` collection fields the same way the existing rules already restrict profile documents to their own owner or admin.
- **Victim GPS coordinates are similarly sensitive** — this is why `SituationMap.tsx` (admin, exact pins) and `PublicSeverityMap.tsx` (public, district aggregates only) are two separate pages backed by two separate endpoints, not one page with a role check. Don't let a "quick win" shortcut (e.g. reusing the admin map's data source for the public page) leak exact locations publicly.
- **Correction to a long-standing wrong assumption:** earlier handoffs of this file claimed Firestore was "still in test mode" with `firestore-rules/firestore.rules` unedeployed. That was wrong — while building live `onSnapshot` listeners (see "Live updates" below), a direct unauthenticated Firestore REST read against `aidRequests` succeeded and a read against `broadcasts` (a collection with no rule block at the time) failed with `permission-denied`, which is only possible if real rules matching this file were already deployed and actively enforced. Nobody had verified this either way before; it was just repeated across handoffs. `firestore-rules/firestore.rules` is now confirmed deployed via `firebase deploy --only firestore:rules` (project `disaster-aid-system`, config in `firebase.json`/`.firebaserc` at the repo root) and covers all six collections: `users`, `aidRequests`, `donations`, `deliveries`, `broadcasts`, `categoryLimits`, `caseNotes`. **Lesson for future sessions: don't take a prior handoff's infrastructure claims (deployed/not deployed, configured/not configured) at face value — verify empirically when it becomes load-bearing, the way this was.**

## Coding conventions established so far

- Every backend route validates required fields and returns `{ error: "..." }` with an appropriate HTTP status on failure.
- Frontend pages: self-contained function components, `useState`/`useEffect` only, no external state library.
- `apiFetch()` in `web/src/lib/api.ts` is the only sanctioned way the frontend calls the backend.
- Tailwind utility classes only.
- Firestore field names camelCase; every write sets `createdAt`/`updatedAt` as ISO strings, not Firestore Timestamps.
- New rule going forward: any field or endpoint touching NIC, home address, or exact victim location gets a one-line comment noting it's sensitive and why it's restricted the way it is — makes the constraint visible to whoever edits that code next, not just documented here.
